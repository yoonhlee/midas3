# 채용공고 지도 데이터 처리 방법 ("지금 이 일을 뽑는 곳")

결과 화면 마지막 섹션은 체험한 직업의 **지금 지원할 수 있는 고용24 채용공고**를 근무지 기준으로 지도·목록에 보여줘.
판정이나 추천은 하지 않고, 공식 공고를 출처·기준 시점·조회 조건과 함께 그대로 보여주는 게 전부야.
그래서 아래의 모든 처리 단계를 숫자로 검증할 수 있게 남겨.

> **현재 상태(2026-10-26)**: 작업 환경에 고용24 채용정보 인증키(`WORK24_RECRUIT_AUTH_KEY`)와 카카오 REST API 키가 없어서
> **실제 수집은 아직 한 번도 돌리지 않았어.** 5장의 "실제 데이터" 표는 비어 있고, 아래 숫자는 모두 고정 데이터(가짜 공고)로
> 처리 파이프라인을 검증한 값이야. 키를 넣고 `npm run postings:refresh -- --verbose`를 돌리면 `reports/postings/quality.json`에
> 실제 값이 생기니, 그 값으로 5장 표를 채워.

---

## 1. 데이터 출처와 조회 조건

| 항목 | 값 |
|---|---|
| API | 고용24 채용정보 목록 Open API `callOpenApiSvcInfo210L01.do` (`callTp=L`, `returnType=XML`) |
| 직종 조건 | `occupation` = 직업별 고용24 직종코드(여러 개는 `\|`로 연결). 직종 미정 직업은 수집하지 않음 |
| 등록 기간 | `regDate=M-1`(최근 한 달, `POSTINGS_REG_DATE`로 변경 가능) |
| 정렬 | `sortOrderBy=DESC`(등록일 최신순) |
| 페이지 | `display=100`, 직업당 최대 10페이지(1,000건, `POSTINGS_MAX_PAGES`). 받은 건수가 `total`에 닿거나 한 페이지가 100건 미만이면 멈춤 |
| 기업형태 | 같은 조건에 `coTp=01`(대기업), `04`(공공기관), `05`(외국계)를 하나씩 붙여 따로 조회하고, 공고번호 집합으로 표시 |
| 호출 간격 | 순차 호출, 호출 사이 300ms, 네트워크 오류·5xx만 1회 재시도, 타임아웃 15초 |
| 갱신 주기 | 서버 시작 30초 뒤 한 번, 이후 1시간마다 확인해 스냅샷이 24시간(`POSTINGS_REFRESH_HOURS`)보다 오래됐으면 갱신 |
| 화면 요청 | 결과 화면은 저장된 스냅샷만 읽어. 사용자 요청마다 외부 API를 부르지 않아 |
| 정리 순서 | 중복 제거(`wantedAuthNo`) → 조건 적용 검증(4.4) → 마감 공고 제외(한국 시간 오늘보다 마감일이 이르면) → 제목 필터 |
| 주소 | 근무지 `basicAddr`만 사용. `detailAddr`(층·호수)는 표시·지오코딩 모두 쓰지 않아. 회사(본사) 주소로 대신하지 않아 |

## 2. 직종 연결

### KNOW 코드와 고용24 코드는 분류 버전이 달라

KNOW 직업정보의 `kecoCd`는 4자리 고용직업분류(KECO)이고, 고용24 공고의 `jobsCd`는 다른 버전의 6자리 세분류야.
예를 들어 데이터분석가의 KNOW KECO는 `1341 데이터 전문가`인데, 고용24에서 `134100`은 **네트워크 시스템 개발자**이고
데이터 분석가는 `135200`이야. 그래서 KNOW 코드 앞자리로 고용24 코드를 추정하지 않고, 검증한 매핑 파일
`data/postings/occupation_map.json`으로 관리해.

### 직업별 매핑

| KNOW 직업 | KNOW KECO | 방식 | 고용24 직종코드 | 근거 |
|---|---|---|---|---|
| K000000872 광고·홍보·마케팅전문가 | 0241 광고·홍보 전문가 | code | `024101` 광고·홍보 전문가, `024102` 마케팅 전문가 | 고용24 직종표(2026-10, 운영 중인 수집 코드의 직종표) |
| K000000997 상품기획자 | 0243 상품 기획자 | code | `024301` 상품 기획자 | 같은 직종표. `024302` 머천다이저는 다른 직업이라 제외 |
| K000001080 데이터분석가 | 1341 데이터 전문가 | code | `135200` 데이터 분석가(빅데이터 분석가) | 같은 직종표. 고용24 1341xx는 다른 직종 |
| K000001179 투자분석가 | 0311 투자·신용 분석가 | **미정(tbd)** | - | 인증키가 없어 직종코드 탐색을 못 돌림 |
| K000007519 보험상품개발자 | 0313 보험·금융상품 개발자 | **미정(tbd)** | - | 같은 이유 |

미정 직업은 화면에 "이 직업은 공고 연결을 준비 중이야"가 떠.

### 미정 직업을 정하는 방법 (`npm run postings:discover`)

1. 후보 키워드로 목록을 조회해(투자분석가: 투자분석·애널리스트·신용분석, 보험상품개발자: 보험상품·상품개발).
2. 응답 공고의 `jobsCd`별 빈도와 대표 제목 5개를 모아.
3. 빈도 상위 5개 코드마다 `infoSvc=VALIDATION` 공고 1건의 상세 API로 직종명(`jobsNm`)을 얻어.
4. 직종명에 KNOW 직업명(KECO)의 핵심어가 2개 이상 들어 있으면 "채택 제안"으로 표시해(예: 투자·신용 분석가 → 투자, 신용, 분석).
   이건 보조 표시이고, **같은 일을 가리키는지는 사람이 표를 보고 최종 결정**해. 깔끔한 코드가 없으면 키워드 검색 + 제목 필터(`mode: keyword`)를 제안해.
5. 결과는 `docs/postings_occupation_discovery.md`에 표(코드·직종명·빈도·대표 제목·결정)로 남고, `--apply`를 붙이면 매핑 파일에 기록돼.

## 3. 지역 판정 규칙

**우선순위**: 도로명코드(`strtnmCd`) → `region` 텍스트 → `basicAddr` 텍스트 → 카카오 지오코딩의 `region_1depth_name`

**도로명코드**: 12자리 중 앞 2자리가 시도 코드야. 통합·개편 전 코드도 현재 시도로 모아.

| 코드 | 시도 | 코드 | 시도 |
|---|---|---|---|
| 11 | 서울 | 41 | 경기 |
| 26 | 부산 | 42(옛 강원도), 51 | 강원 |
| 27 | 대구 | 43 | 충북 |
| 28 | 인천 | 44 | 충남 |
| 29(옛 광주광역시), 46(옛 전라남도), 12 | 전남광주 | 45(옛 전라북도), 52 | 전북 |
| 30 | 대전 | 47 | 경북 |
| 31 | 울산 | 48 | 경남 |
| 36 | 세종 | 50 | 제주 |

**2026-07-01 전남광주 통합 반영**: 광주광역시와 전라남도가 전남광주통합특별시(약칭 광주특별시)로 통합됐어.
옛 코드 29·46과, 참고 구현이 통합 후 코드로 쓰는 `12`(공식 확인 필요)를 모두 "전남광주"로 처리해.
문자열도 광주·광주광역시·광주특별시·전남·전라남도·전남광주·전남광주통합특별시를 모두 "전남광주"로 모아.
(전체 대응표: `src/lib/postings/regions.ts`의 `SIDO_ALIASES`. 단위 테스트가 표 전체를 검사해.)

**수도권** = 서울·인천·경기. 나머지는 비수도권. 판정할 수 없으면 미분류로 두고 요약에서 따로 세("지역을 알 수 없는 공고는 N건이야").

## 4. 위치 정확도 구분

| 값 | 의미 | 화면 |
|---|---|---|
| `address` | 카카오 응답이 `ROAD_ADDR`/`REGION_ADDR`(도로명·지번 주소 좌표) | 작은 점 마커("정확한 위치") |
| `region` | 카카오 응답이 `ROAD`/`REGION`(도로·행정구역 중심)이거나, 주소가 없어 `region` 텍스트("서울 강남구")로 찾은 좌표 | 반투명 큰 원("구·군 단위 대략 위치") |
| `none` | 좌표 없음(주소·지역 모두 실패) | 지도에 없고 목록에만 "지도에 없음"으로 표시 |

좌표가 한국 범위(위도 33~39, 경도 124~132)를 벗어나면 버려. 지오코딩 결과는 `reports/postings/geocode-cache.json`에
캐시하고, 실패는 7일 뒤에 다시 시도해. 좌표를 임의로 만들지 않아(가짜 좌표는 고정 데이터 모드에서만).

## 5. 품질 지표

갱신할 때마다 자동으로 계산해서 스냅샷의 `counts`/`checks`와 `reports/postings/quality.json`에 저장해.

| 지표 | 계산 |
|---|---|
| 공고 수 | 받은 수(`received`), 중복 제거 수, 마감 제외 수, 필터 제외 수(제목 필터 + 직종 불일치 + 등록기간 초과), 최종 수(`kept`) |
| 좌표 성공률 | 최종 공고 중 정확 / 대략 / 실패 비율 |
| 시도 판정 교차 일치율 | 도로명코드로 정한 시도와 카카오 지오코딩 시도가 같은 비율(둘 다 있는 공고만) |
| 제목 키워드 일치율 | 최종 공고 중 제목에 `relevance_keywords`가 하나라도 들어간 비율. 직종 연결 정확도의 대략적인 지표(필터에는 안 씀) |
| 조건 적용 검증 | 아래 규칙. 결과는 "적용 / 무시됨 / 확인 못 함" |

**조건 적용 검증 규칙** (고용24가 급여형태 조건을 조용히 무시한 운영 사례가 있어서 응답으로 확인해)

- 직종: 받은 공고의 95% 이상이 요청한 `jobsCd` 중 하나여야 적용. 아니면 "무시됨"으로 기록하고 요청 코드에 맞는 공고만 남겨.
- 등록 기간: `regDt`가 오늘 기준 32일 이내인 비율이 95% 이상이어야 적용. 아니면 "무시됨"으로 기록하고 32일 넘은 공고를 빼.
- 기업형태: `coTp` 조회의 `total`이 기본 조회 `total`과 같고 20건 이상이면 "무시됨"으로 보고 그 기업형태 표시를 꺼. 조회 자체가 실패하면 "확인 못 함"으로 두고 역시 표시를 꺼.

## 6. 사람 검토용 표본

제목 키워드 일치율은 대략적인 지표라서, 직종 연결 정확도는 사람이 직접 재는 게 좋아.

1. `npm run postings:sample` → 직업별 무작위 20건(회사·제목·직종코드)이 `docs/postings_sample_review.md`에 생겨.
   같은 표본을 다시 만들려면 `-- --seed 2026-10-26`처럼 seed를 지정해.
2. 각 줄의 `[ ]` 안에 `O`(이 직업 공고가 맞음) 또는 `X`(아님)를 적어. 회사·제목·직종코드만 보고 판단해.
3. `npm run postings:sample -- --tally` → 직업별 `O`, `X`, 미체크 수와 **정확도 = O ÷ (O + X)** 가 표로 나와.
4. 보고서에는 정확도와 함께 표본 수(O+X)를 같이 적어. 20건 표본이면 정확도 90%의 95% 신뢰구간이 대략 ±13%p라서,
   직업 간 차이를 말할 때는 표본 수를 늘려(`--size 50`).

## 7. 한계

- 고용24에 등록된 공고만 다뤄. 대기업 자체 채용 사이트 공고는 빠질 수 있어.
- 최근 한 달 단위 스냅샷이야. 실시간이 아니고, 마감 판정은 스냅샷 시점 기준이야.
- 고용24 직종 분류 자체에 오차가 있을 수 있어(제목은 데이터 분석인데 다른 직종코드로 등록된 공고 등).
- 기업형태는 고용24 분류(`coTp`) 기준이야. 응답에 없는 기업형태는 추정하지 않아.
- 좌표는 카카오 주소 검색 결과야. 주소가 부정확하면 대략 위치나 좌표 없음으로 남아.
- 전남광주 통합 후 시도 코드(`12`)는 참고 구현 기준이라 공식 확인이 필요해.
- 지도 타일은 OpenStreetMap 공용 서버야. 정식 서비스로 확장하면 타일 제공자를 바꿔야 해.
